# Implementation log

Questions that came up while implementing the system without the project owner present, and the decision taken for each. Behaviour where the standard is silent is recorded in REQUIREMENTS.md Part E as REQ-DOC-004 requires; this log covers implementation and scope choices.

Started 10 October 2026. Instruction: implement the whole system, targeting only amd64 and iTerm2 for now.

| # | Question | Decision | Reason |
|---|---|---|---|
| 1 | What does "amd64 only" mean for build and test? | Build and test for `x86_64-unknown-linux-gnu` (on `oldvga`) and `x86_64-apple-darwin` (on the Mac under Rosetta, where iTerm2 runs). The `no_std` crates are also built for `x86_64-unknown-none`, the amd64 bare-metal target, so they stay honestly `no_std`. Day-to-day iteration runs natively on the Mac. | iTerm2 exists only on macOS, so the amd64 build that iTerm2 users run is `x86_64-apple-darwin`. Linux is where the Phase 1 sandbox lives. |
| 2 | Which toolchain? | Rust 1.99.0, pinned in `rust-toolchain.toml`. | REQ-GEN-001; the current stable release. |
| 3 | Which terminal graphics protocols? | iTerm2 inline images only. kitty and Sixel are deferred. | Scope given by the project owner. |
| 4 | Continuous integration or local gates? | Local gates only: `scripts/check.sh` runs every check, and git hooks run it (fast on pre-commit and pre-push). *Amended 11 October 2026:* the full gate grew to about 40 minutes, so the owner had it taken off pre-push; it is run before merging to main and before a release. | The owner's standing rule is "no CI unless asked"; it overrides the CI wording of REQ-TST-080. |
| 5 | Commit while working? | Work on branch `implementation`, one commit per completed part. | The instruction to finish the whole system unattended implies saving progress; a branch keeps `main` untouched. |
| 6 | Where do constants that are not teletext values live, such as the transport stream sync byte 0x47 or WebSocket opcodes? | Teletext values (EN 300 706) are only in `neoteletext-core::consts`. Values of other standards used by one crate (EN 300 472 transport streams, RFC 6455, HTTP) live in that crate's own `consts` module, each defined once. Core constants are reused, never restated. | REQ-GEN-014 names teletext values; a single module for every protocol's numbers would couple the core to the web and transport layers. |
| 7 | How do TTI Link Extension links (`LN`) and form commands reach the viewer, given that pages enter the decoder only as packets (REQ-ARCH-004)? | The TTI reader yields the page and its extension data separately. The page is encoded to packets (X/27/0 and X/24 per Appendix E.2) for the decoder; the application keeps the extension data (links, forms) in a side table keyed by page and sub-code, and the viewer reads it to draw row 24 and run forms. | Keeps one decode path, while the receiver-drawn row and other-service links, which packets cannot carry, still reach the viewer. |
| 8 | Which line of the 6 by 10 cell is the blank one? | Cell line 0 (the top) is blank and glyph rows 0 to 8 occupy lines 1 to 9. | SAA5050 geometry: the 5 by 9 matrix sits under a blank line, leaving descenders at the bottom; this matches REQ-RND-011's split of lines 1 to 5 and 6 to 10. To be checked against reference images (REQ-TST-030). |
| 9 | How should the glyphs drawn ambiguously in the standard's tables be mapped (Rumanian cedilla or comma, Greek tonos, Arabic contextual forms, G3 line pieces)? | As listed in the charset transcription notes, summarised in `crates/neoteletext-core/src/charset/tables.rs` comments: cedilla forms for Rumanian, ISO 8859-7 forms for Greek, Arabic presentation forms by joining side, heavy-light box drawing for G3 joins. | The tables are pictures; each choice is the closest Unicode reading and is to be cross-checked against zvbi's reference mapping (REQ-TST-011). |
| 10 | `rustfmt` and hand-aligned tables? | `rustfmt.toml` sets width 120; the two data tables are `#[rustfmt::skip]` at their `mod` line. | REQ-GEN-006 requires rustfmt; the tables are easier to check against the standard in their aligned form. |
| 11 | Clippy's `struct_excessive_bools` and `match_same_arms` on teletext state? | Allowed only at the site, with the reason written there (cell attributes listed by REQ-L1-001; one match arm per state table row). | The owner's rule forbids blanket suppression. |
| 12 | What do the digit keys give in remote-control letter entry (REQ-NAV-009 "as on a telephone keypad")? | ITU E.161 letters: 2 ABC, 3 DEF, 4 GHI, 5 JKL, 6 MNO, 7 PQRS, 8 TUV, 9 WXYZ; 1 gives `. , - @ _ 1`; 0 gives space then 0. Repeated presses of the same key within 1 second cycle through its characters; a different key or a pause commits. Letters are entered in upper case. | E.161 is the keypad standard; `@` on key 1 lets email fields be filled from a remote. |
| 13 | How is the status area shown in 7 columns for states the spec lists (sub-page, stale, unencrypted, confirmations)? | `P100` normally; `P100/02` for a chosen sub-page (its position among stored sub-pages); `P100 ?` when stale; a red attribute then the number and `!` for plain HTTP; red `HTTP?` while a plain-HTTP submission awaits confirmation; yellow `LEAVE?` while a link to another service awaits confirmation. | Every indicator stays inside columns 0 to 6, which pages cannot write (REQ-SEC-005); colours are receiver attributes in column 0. |
| 14 | Use the `png` crate for image output (REQ-RND-007 permits it)? | No. `neoteletext-image` has its own small PNG encoder: indexed colour (the 144-entry palette, with `tRNS` for transparency), fixed-Huffman deflate with run-length and previous-row matches, split into bounded IDAT chunks so it streams in fixed memory. | Keeps the image helpers dependency-free and `no_std` (decision E.38). Teletext pages compress very well with exactly these two match kinds, which keeps iTerm2 inline images small. |

| 26 | How is web and live mode separated into processes (REQ-SEC-018), and on which systems? | On every system, `neottx view <live source>` starts `neottx fetch <source>` (a hidden command) as a child before sandboxing. The child holds the network and runs the web module with a `rustls` transport; the parent decodes and draws with no network. They talk over the child's standard input and output in framed messages: child to parent `P` packet (42 bytes), `T` TTI or `B` T42 page bytes, `N` notice; parent to child `R` page request. Each side bounds every frame (at most 256 KiB, the page limit) and rejects unknown kinds. On Linux both processes are sandboxed (the fetcher may read `/etc` for name resolution); on macOS neither is (decision 15). | One code path everywhere keeps the design testable; the frame set is the "small, fixed set of framed control messages" REQ-SEC-018 asks for. |
| 27 | Does the transport also refuse blocked addresses, or only the web module after connecting? | Both. | 34 | How does `neottx` work offline (REQ-WEB-009) without changing the normative page lifecycle table of REQ-FSM-004? | A server's "unchanged" answer (304, or still fresh in the cache) is treated as receiving the same page again: the fetcher sends a `K` (current) notice and the decoder side feeds the page's last bytes in again, which moves a stale page back to complete through the existing transitions. A fetch that fails for want of a network sends an `O` (offline) notice; if that page is not stored, the viewer shows "Page not available offline" in row 24. Stored pages stay viewable and go stale after `stale_after_us` (60 s), shown by "?" in the status area. Tested by `tests/web-server/drive_offline.py`, which stops and restarts the server under a running viewer. | Keeps one lifecycle machine for broadcast and web pages, as REQ-WEB-005 asks. |
