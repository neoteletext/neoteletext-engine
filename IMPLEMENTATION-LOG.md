# Implementation log

Questions that came up while implementing the system without the project owner present, and the decision taken for each. Behaviour where the standard is silent is recorded in REQUIREMENTS.md Part E as REQ-DOC-004 requires; this log covers implementation and scope choices.

Started 10 October 2026. Instruction: implement the whole system, targeting only amd64 and iTerm2 for now.

| # | Question | Decision | Reason |
|---|---|---|---|
| 1 | What does "amd64 only" mean for build and test? | Build and test for `x86_64-unknown-linux-gnu` (on `oldvga`) and `x86_64-apple-darwin` (on the Mac under Rosetta, where iTerm2 runs). The `no_std` crates are also built for `x86_64-unknown-none`, the amd64 bare-metal target, so they stay honestly `no_std`. Day-to-day iteration runs natively on the Mac. | iTerm2 exists only on macOS, so the amd64 build that iTerm2 users run is `x86_64-apple-darwin`. Linux is where the Phase 1 sandbox lives. |
| 2 | Which toolchain? | Rust 1.99.0, pinned in `rust-toolchain.toml`. | REQ-GEN-001; the current stable release. |
| 3 | Which terminal graphics protocols? | iTerm2 inline images only. kitty and Sixel are deferred. | Scope given by the project owner. |
| 4 | Continuous integration or local gates? | Local gates only: `scripts/check.sh` runs every check, and git hooks run it (fast on pre-commit, full on pre-push). | The owner's standing rule is "no CI unless asked"; it overrides the CI wording of REQ-TST-080. |
| 5 | Commit while working? | Work on branch `implementation`, one commit per completed part. | The instruction to finish the whole system unattended implies saving progress; a branch keeps `main` untouched. |
| 6 | Where do constants that are not teletext values live, such as the transport stream sync byte 0x47 or WebSocket opcodes? | Teletext values (EN 300 706) are only in `tellytxt-core::consts`. Values of other standards used by one crate (EN 300 472 transport streams, RFC 6455, HTTP) live in that crate's own `consts` module, each defined once. Core constants are reused, never restated. | REQ-GEN-014 names teletext values; a single module for every protocol's numbers would couple the core to the web and transport layers. |
| 7 | How do TTI Link Extension links (`LN`) and form commands reach the viewer, given that pages enter the decoder only as packets (REQ-ARCH-004)? | The TTI reader yields the page and its extension data separately. The page is encoded to packets (X/27/0 and X/24 per Appendix E.2) for the decoder; the application keeps the extension data (links, forms) in a side table keyed by page and sub-code, and the viewer reads it to draw row 24 and run forms. | Keeps one decode path, while the receiver-drawn row and other-service links, which packets cannot carry, still reach the viewer. |
| 8 | Which line of the 6 by 10 cell is the blank one? | Cell line 0 (the top) is blank and glyph rows 0 to 8 occupy lines 1 to 9. | SAA5050 geometry: the 5 by 9 matrix sits under a blank line, leaving descenders at the bottom; this matches REQ-RND-011's split of lines 1 to 5 and 6 to 10. To be checked against reference images (REQ-TST-030). |
| 9 | How should the glyphs drawn ambiguously in the standard's tables be mapped (Rumanian cedilla or comma, Greek tonos, Arabic contextual forms, G3 line pieces)? | As listed in the charset transcription notes, summarised in `crates/tellytxt-core/src/charset/tables.rs` comments: cedilla forms for Rumanian, ISO 8859-7 forms for Greek, Arabic presentation forms by joining side, heavy-light box drawing for G3 joins. | The tables are pictures; each choice is the closest Unicode reading and is to be cross-checked against zvbi's reference mapping (REQ-TST-011). |
| 10 | `rustfmt` and hand-aligned tables? | `rustfmt.toml` sets width 120; the two data tables are `#[rustfmt::skip]` at their `mod` line. | REQ-GEN-006 requires rustfmt; the tables are easier to check against the standard in their aligned form. |
| 11 | Clippy's `struct_excessive_bools` and `match_same_arms` on teletext state? | Allowed only at the site, with the reason written there (cell attributes listed by REQ-L1-001; one match arm per state table row). | The owner's rule forbids blanket suppression. |
| 12 | What do the digit keys give in remote-control letter entry (REQ-NAV-009 "as on a telephone keypad")? | ITU E.161 letters: 2 ABC, 3 DEF, 4 GHI, 5 JKL, 6 MNO, 7 PQRS, 8 TUV, 9 WXYZ; 1 gives `. , - @ _ 1`; 0 gives space then 0. Repeated presses of the same key within 1 second cycle through its characters; a different key or a pause commits. Letters are entered in upper case. | E.161 is the keypad standard; `@` on key 1 lets email fields be filled from a remote. |
| 13 | How is the status area shown in 7 columns for states the spec lists (sub-page, stale, unencrypted, confirmations)? | `P100` normally; `P100/02` for a chosen sub-page (its position among stored sub-pages); `P100 ?` when stale; a red attribute then the number and `!` for plain HTTP; red `HTTP?` while a plain-HTTP submission awaits confirmation; yellow `LEAVE?` while a link to another service awaits confirmation. | Every indicator stays inside columns 0 to 6, which pages cannot write (REQ-SEC-005); colours are receiver attributes in column 0. |
| 14 | Use the `png` crate for image output (REQ-RND-007 permits it)? | No. `tellytxt-image` has its own small PNG encoder: indexed colour (the 144-entry palette, with `tRNS` for transparency), fixed-Huffman deflate with run-length and previous-row matches, split into bounded IDAT chunks so it streams in fixed memory. | Keeps the image helpers dependency-free and `no_std` (decision E.38). Teletext pages compress very well with exactly these two match kinds, which keeps iTerm2 inline images small. |
| 15 | `ttx` on macOS, where sandboxing is Phase 2 (REQ-SEC-017): refuse to run, or run? | Run, with a one-line notice on standard error that macOS sandboxing is not implemented yet. On Linux, where it is Phase 1, `ttx` refuses to run if Landlock cannot be applied unless `--no-sandbox` is given. | The refusal rule concerns a sandbox that exists but cannot be applied; on macOS no Phase 1 mechanism exists, and refusing would make the iTerm2 target unusable. Recorded as a gap for the Phase 2 work. |
| 16 | Which crates may `ttx` (std only, never on a microcontroller) use? | `clap` (command line, REQ-GEN-017 names it), `crossterm` (raw mode, keys and the terminal's pixel size for the interactive viewer and iTerm2 sizing), and on Linux only `landlock` and `seccompiler` for REQ-SEC-017. TLS for web mode: `rustls` with `webpki-roots` (decided when web mode is wired). | All are permissively licensed and widely used; the CLI is judged by normal rules (decision E.38). The sandbox crates give safe APIs, so `ttx` itself stays free of `unsafe`. |
| 17 | How is iTerm2 detected (REQ-RND-029 says by querying the terminal)? | `TERM_PROGRAM=iTerm.app` or `LC_TERMINAL=iTerm2` in the environment, refused inside tmux or GNU screen (`TMUX`, `STY`) with a diagnostic; `--graphics iterm2|text` forces either. The XTVERSION query is not used yet. | iTerm2 sets these variables itself, including over ssh for `LC_TERMINAL`; an escape-sequence query needs raw mode and a timeout and adds failure modes for no gain while iTerm2 is the only protocol. |
| 18 | How are the gates enforced, and what about tools not installed (cargo-deny, cargo-fuzz, Miri)? | `scripts/check.sh fast|full`; hooks live in `.githooks/` and are enabled with `git config core.hooksPath .githooks`. Tools that are not installed are reported as SKIPPED, never silently passed. Installing them is left to the owner. | The owner's rule: one local script runs every gate, hooks enforce it, and nothing is installed reflexively. |
| 19 | Include the interactive terminal viewer (REQ-CLI-004, Phase 2)? | Yes, as `ttx view`: the core viewer machine driven by crossterm keys, drawn as iTerm2 images or ANSI text. Keys: digits enter pages; `r` `g` `y` `c` or F1 to F4 the Fastext keys; `i` Index; `Home` or `h` the initial page; Up and Down next and previous page; Left and Right sub-pages; `?` reveal; `H` hold; `m` mix; `z` zoom; Backspace or Alt-Left back; Alt-Right forward; `q` or Esc quits. | "Implement the entire thing" includes the viewer, and it is the natural way to use the receiver in iTerm2. |
| 20 | Where does the corpus live, and may the TSDuck recordings be used? | `TELLYTXT_CORPUS=~/devel/tellytxt-corpus`, filled by `cargo xtask corpus`, with Dan Farrimond's captures linked in as `dan/`. The first 4 MB of each FFmpeg sample and 8 MB of each TSDuck recording are fetched, and their SHA-256 sums are pinned in `tests/corpus-manifest.txt`. TSDuck's licence page covers its software, not the streams; the streams are used only at test time and never committed. | REQ-TST-022 asks for the licence to be checked and recorded before use, and for ranged requests to keep runs short. |
| 21 | The slicer measured how often the one-bit framing tolerance of decision E.24 accepts false packets: random data after a genuine run-in gives a packet with a valid address on 5.9% of lines tolerant versus 0.34% strict, and VPS-shaped lines 2.1% versus 0.16%. Change the default? | **Open for the owner.** The default stays as E.24 states (tolerant), since REQ-DOC-004 requires a Part E amendment before behaviour changes. A likely amendment is to allow the one-bit tolerance only at the expected framing position, or only on lines already seen carrying teletext. | Measured on synthetic lines (crates/tellytxt-slicer tests). Real VHS recordings have not been compared yet (REQ-TST-061 is not done). |
| 22 | The slicer's measured limits: whole packets survive a bit-rate error of only ±0.05% with the Phase 1 fixed bit period (addresses survive ±0.5%); echoes of 0.4 at 500 ns cut whole packets to 61–85%. | Accepted as Phase 1 behaviour; the Phase 2 tracking loop (REQ-SLC-006) and equalisation (REQ-SLC-011) address them. | Measured, reported, not hidden. |
| 23 | Web protocol details the requirements leave open (descriptor member names, subscription syntax, retries, cookie expiry without a clock, IPv6 origin comparison, SSE Accept header)? | Recorded as decision E.39 in REQUIREMENTS.md, with REQ-WEB-014 amended for `Accept: text/event-stream`. | REQ-DOC-004: behaviour the standard leaves open is recorded in Part E. |
| 24 | Web crate items not done: fuzz targets, the local test server of REQ-WEB-013, stack measurement on Cortex-M. | NOT DONE for now: fuzzing needs `cargo-fuzz` and a nightly toolchain (not installed); the tests use the exact-replay in-memory transport; stack use is irrelevant to the amd64 targets of this round. `Descriptor::parse` builds a structure of about 12 KiB, to be checked before microcontroller ports. | Recorded rather than dropped. |
| 25 | Broadcasters such as TVP (2023) send no X/28 or M/29 packets, so decision E.4 falls back to the configured region, and Polish text decoded as English ("Pi¾ka" for "Piłka"). How should `ttx` configure the region? | `--region N` sets it explicitly. Otherwise, when a transport stream's teletext descriptor names a language, the region is set from it: Polish group 1; Turkish group 2; Serbian, Croatian, Slovenian and Romanian group 3; Russian, Bulgarian, Ukrainian, Estonian, Latvian and Lithuanian group 4; Greek group 6; Arabic group 8; Hebrew group 10; anything else group 0. | E.4 already makes the region a receiver setting; deriving it from the stream's own language label is the application configuring it, not new decoder behaviour. Verified on the TVP 2023 recording. |
| 26 | How is web and live mode separated into processes (REQ-SEC-018), and on which systems? | On every system, `ttx view <live source>` starts `ttx fetch <source>` (a hidden command) as a child before sandboxing. The child holds the network and runs the web module with a `rustls` transport; the parent decodes and draws with no network. They talk over the child's standard input and output in framed messages: child to parent `P` packet (42 bytes), `T` TTI or `B` T42 page bytes, `N` notice; parent to child `R` page request. Each side bounds every frame (at most 256 KiB, the page limit) and rejects unknown kinds. On Linux both processes are sandboxed (the fetcher may read `/etc` for name resolution); on macOS neither is (decision 15). | One code path everywhere keeps the design testable; the frame set is the "small, fixed set of framed control messages" REQ-SEC-018 asks for. |
| 27 | Does the transport also refuse blocked addresses, or only the web module after connecting? | Both. The `ttx` transport resolves the name and refuses to connect to any address the policy blocks (REQ-SEC-006), so no packet is ever sent to the local network; the web module checks again on the reported peer. | Defence in depth: checking only after connecting would still let a forged name reach a router with a TCP handshake. |
| 28 | The sandboxed fetcher could not resolve names on Ubuntu: glibc loads its name-service modules from `/usr/lib` at the first lookup, and `/etc/resolv.conf` links into `/run/systemd/resolve`. What may the fetcher read? | Read-only: `/etc`, `/run/systemd/resolve`, `/usr/lib`, `/lib`, `/usr/lib64` and `/lib64`, where they exist. No write access anywhere, no other paths. The decoder process stays without any file access. | Measured failure on oldvga; these are the directories the C library's resolver needs. Write access and every other path stay denied. |
